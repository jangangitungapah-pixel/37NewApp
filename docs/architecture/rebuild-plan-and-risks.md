# Rebuild Plan, Scope & Risk Register — 37MusicStudio

## 1. Scope & Urutan Fase (Strict Phase Gates)

Setiap fase dikerjakan satu per sesi dan harus lulus phase gate serta memiliki dokumentasi checkpoint + timestamped verification log `.txt` + handoff prompt `.txt` sebelum berpindah ke fase berikutnya.

| Phase | Nama Fase | Ruang Lingkup & Deliverable Utama | Gate Kriteria Selesai |
| :--- | :--- | :--- | :--- |
| **00** | Discovery, Repository Audit & Architecture Lock | Audit repo & toolchain lokal, audit read-only Firebase projects eksisting, inisialisasi Git lokal, ADR-0001, scope, risk register, checkpoint & handoff Phase 01. | Audit selesai tanpa menyentuh data eksisting; ADR & rencana disusun. |
| **01** | Application Foundation & Firebase Security | Scaffold React + Vite + JS (`src/` modular layout), router, providers, error boundary, `.env.example`, Firebase Auth + Firestore init, `users/{uid}` & `members/{uid}` guards, `firestore.rules` (deny-by-default), `firestore.indexes.json`, `firebase.json`, uji Rules & build lokal. | Login/logout bersih (unsubscribe listeners), guard Owner/Operator aktif, Rules deny-by-default teruji, build produksi sukses. |
| **02** | Business Master Data | CRUD Business profile, Studios/Rooms, Operating hours (`Asia/Jakarta`), Services (`Rehearsal`, `Recording`, `Mixing`, `Mastering`), Pricing & Commission policies, Customers, Team membership & `assignedStudioIds`. | Master data tervalidasi schema & Rules; Owner/Operator scope teruji. |
| **03** | Booking Engine & Calendar | Calendar desktop (kolom tanggal, baris jam) & mobile task-oriented UI, availability query, deterministic `bookingSlots` transaction, lifecycle state machine, atomic cancel/reschedule, `activityLogs`, realtime sync antar portal. | Dua client rebutan slot yang sama tidak bisa double-book; failed tx zero orphan; snapshot tersimpan saat confirm. |
| **04** | Session, Settlement, Ledger & Commission | Workflow `IN_PROGRESS` -> `COMPLETED_PENDING_SETTLEMENT`, Owner settlement review, atomic settlement tx (`bookings` + immutable `ledgerEntries` + `commissionEntries` + `activityLogs` + `notifications`), adjustment/reversal entries, commission view Operator. | Retry tidak menduplikasi ledger/commission; entry historis immutable di Rules; non-Owner ditolak saat settle. |
| **05** | Portal Collaboration & Notifications | Scoped realtime subscription manager, activity timeline, in-app `notifications` per recipient, unread state, cross-portal propagation, stale/offline/permission-denied/connection-error recovery states. | Event lintas portal tampil realtime tanpa refresh; listener selalu cleanup saat unmount/logout. |
| **06** | Gallery & Cloudinary | Restricted unsigned upload adapter, client validation & preview, Firestore `galleryAssets` metadata, caption/ordering/archive flow, responsive Cloudinary CDN delivery, orphan-upload failure recovery UX, manual cleanup guide. | Tidak ada API Secret di client/repo; orphan upload ditangani eksplisit; archived asset tersembunyi dari galeri aktif. |
| **07** | Dashboard, Analytics & Reporting | Owner KPIs, Operator task summary, studio utilization, booking trends, definisi metrik pendapatan vs settlement vs komisi yang konsisten, cursor pagination untuk query historis. | Query laporan hemat Spark quota (tanpa listener global); metrik konsisten dengan ledger & timezone bisnis. |
| **08** | Hardening, Accessibility & Production Readiness | End-to-end verification seluruh Acceptance Criteria (Sec 15), security/Rules/index review, quota & mobile UX audit, keyboard/contrast/`prefers-reduced-motion` QA, production build & checklist deployment ke project Firebase baru. | Seluruh checklist Acceptance Criteria terbukti; log audit lengkap; siap deploy hanya dengan persetujuan eksplisit user. |

## 2. Risk Register & Kontrol Mitigasi

| ID | Risiko | Dampak | Penyebab / Batas Teknis | Kontrol & Mitigasi Wajib |
| :--- | :--- | :--- | :--- | :--- |
| **R-01** | Manipulasi nilai kalkulasi harga/diskon/komisi dari browser yang dimodifikasi | Tinggi (Integritas Finansial) | Spark plan melarang Cloud Functions/backend tepercaya; logic berjalan di client JS. | Batasi hak write sensitif (settlement, pricing/commission settings) ke Owner di `firestore.rules`; kunci validasi field allowlist, tipe integer, batas range/status transition, dan snapshot immutability di Rules; catat append-only `activityLogs`. Tidak mengklaim anti-fraud backend penuh. |
| **R-02** | Eksposur atau penyalahgunaan Cloudinary Unsigned Upload Preset | Sedang (Kuota & Penyalahgunaan Storage) | Unsigned preset harus diketahui browser dan Cloudinary tidak menyediakan per-preset file-size limit untuk unsigned upload. | Gunakan preset khusus yang dibatasi format gambar (`jpg,jpeg,png,webp`), nonaktifkan custom `public_id`, isolasi folder, validasi ukuran/dimensi di client untuk UX, pantau kuota Cloudinary, dan siapkan rotasi nama preset bila terekspos. |
| **R-03** | Orphan file di Cloudinary bila write metadata Firestore gagal | Sedang (Konsistensi Data) | Browser tidak memiliki API Secret Cloudinary sehingga tidak bisa auto-delete saat metadata write gagal. | Tangkap error Firestore pasca-upload secara eksplisit, tampilkan status *Orphan Upload*, sediakan tombol *Retry Save Metadata* dengan hasil upload yang sama (`publicId`, `secureUrl`), dan dokumentasikan prosedur cleanup manual di Cloudinary Console. |
| **R-04** | Transaction contention & batas document access calls di Firestore Rules | Tinggi (Kegagalan Booking Durasi Panjang) | Booking membaca/menulis banyak dokumen `bookingSlots` sekaligus, sementara Rules memiliki batas pemanggilan `get()`/`exists()`/`getAfter()`. | Gunakan bucket default 15–30 menit yang proporsional dengan durasi layanan (maksimum slot per booking dibatasi eksplisit di policy), baca semua slot sebelum write, desain Rules efisien agar tidak boros `getAfter()` per slot. |
| **R-05** | Pembengkakan kuota Firestore Spark (reads/writes/listeners) | Tinggi (Service Throttling) | Listener koleksi global atau re-subscribe berulang dapat menghabiskan kuota gratis Spark (50k reads / 20k writes per hari). | Wajib pakai scoped listeners (filter `businessId`, `studioId`, rentang tanggal aktif), cursor pagination untuk histori/laporan, dan strict unsubscribe di cleanup hook & logout. |
| **R-06** | Transaksi offline dikira sukses oleh user | Tinggi (Double Booking / Data Hilang) | Cache offline Firestore membuat write biasa tampak selesai lokal, padahal Firestore transaction gagal saat offline. | Deteksi network/commit status; larang dan beri feedback jelas untuk critical writes (confirm booking, cancel/reschedule slot, session completion finansial, settlement) saat offline; tandai bacaan cache sebagai `stale`. |
| **R-07** | Perubahan konfigurasi/data pada project Firebase eksisting secara tidak sengaja | Kritis | Terdapat 5 project eksisting pada akun Firebase CLI aktif (`music-studio-2`, `music-studio-f69d8`, `studio-proper`, `studioflutter37`, `jadwalshifting-fd32b`). | Project eksisting dilarang keras dipilih di `.firebaserc`. Gunakan project Firebase baru yang dikonfirmasi eksplisit oleh user sebelum deploy/integrasi live, dan gunakan emulator lokal untuk pengujian sebelum binding project baru. |

## 3. Kebutuhan Binding Sebelum Live Integration (Phase 01+)
Untuk menjalankan Phase 01 secara lokal & teruji di Emulator, tidak perlu menunggu project live. Namun sebelum menyambungkan aplikasi ke environment Firebase/Cloudinary live, user perlu menyediakan:
1. **Project ID Firebase baru** (beserta Web App config: `apiKey`, `authDomain`, `projectId`, `storageBucket` [opsional], `messagingSenderId`, `appId`) untuk `.env.local` dan `.firebaserc`.
2. **Cloudinary Cloud Name** & **Restricted Unsigned Upload Preset** (dibutuhkan pada Phase 06).
3. *(Opsional)* Konfirmasi bila ingin mengubah baseline operasional di ADR-0001 (mis. `slotGranularityMinutes` selain `15` menit, atau mengaktifkan App Check sejak awal).
